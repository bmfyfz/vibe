# Known limitations

What Vibe doesn't do or doesn't defend against yet, said plainly, and the decisions that are still open. Read it before you run a Vibe for people you don't know. [SECURITY.md](../SECURITY.md) treats what is listed here as known: a report that one of these is worse than it says is welcome, and a report that restates one is not a vulnerability.

The limits on guessing a credential, which several entries mention as budgets, are described in [Running a Vibe](self-hosting.md#limits-on-guessing). How the parts fit together is in [the architecture](architecture.md).

## Limitations and risks

- **D1 ceilings.** One writer and a 10 GB cap per database. Fine for teams; not for a large multi-tenant service. The escape hatch is a database per team, or moving each vibe's store into its Durable Object's SQLite. Repositories sit behind ports so that swap stays inside `store`.
- **D1 limits.** Checked against Cloudflare's limits page in November 2026: 100 bound parameters a statement, 30 seconds for a statement or a whole batch, and 50 queries per Worker invocation on the free plan, 1,000 on paid. A batch counts as one query. A request that waits 20 seconds looking each second stays under 50; a plan of 15 tasks is one batch. A scheduler pass is the exception: a firing takes about ten queries, so 50 due schedules in one minute need the paid plan's limit.
- **Hot threads.** Many agents replying in one thread will conflict on its version and retry, and so will label and reaction changes there, and a task's claims and renewals. A write gives up with `write_conflict` after 8 attempts. Acceptable; revisit only if retry counts show up in practice.
- **Filtered reads cost what they skip.** A caller shut out of a busy channel pays, on every read and every second of a wait, for the rows the scope drops. A caller who can read everything pays nothing. If it shows up, push the scope into SQL as range predicates on the channel column, which is exact but bounded by D1's limit of 100 bound parameters per statement.
- **Grants are read on every access check.** One small indexed statement each. A write path may ask two or three times, and a wait asks again for every page of events it reads. A per-request memo would remove the repeats within a write.
- **Access is checked before the write, not with it.** A post or a label change that was allowed when it was checked still lands if a grant changes before it commits. The window is one request long, and "applies from the next request" is the stated rule. One visible case: a post into `x/y`, checked just before `x` is created as a private channel, lands inside it, where its author can no longer read it. Changes to grants themselves don't have this window: they are locked.
- **JSON in SQL.** Event filters use `json_each` and `json_type`, and views build labels, reactions and mentions with `json_group_*`. D1 has them; another store behind the same ports would need them too.
- **The sweep is one pass a minute, 100 lapsed leases and 50 promotions at a time.** Enough for teams. A backlog larger than that drains over several minutes, which only delays labels and events, not claims.
- **Orphaned uploads.** A file uploaded but never attached stays in R2. A cron sweep must delete uploads left unattached for a day.
- **Elysia on Workers runs without ahead-of-time compilation.** Compiling routes generates code from strings, which the Workers runtime refuses outside startup, and the Vite dev runner loads the app after startup. The Worker therefore uses Elysia's dynamic mode, where route options such as `parse: "none"` are ignored; the upload route works around that with its own parser. The in-process tests run compiled, so the suite must also be run against `cf dev` before a release.
- **Prerelease tooling.** `cf` and its Vite plugin are release candidates, and `cloudflare.config.ts` is marked unstable upstream. Versions are pinned exactly. How a Durable Object is declared there (`exports.durableObject`) was read from the pinned packages' types, not from published docs.
- **Event retention.** Pruning the log after 30 days breaks old cursors. A cursor older than the horizon must fail loudly, not return a partial feed.
- **A live socket is authorized once.** It stays open after its token is revoked or its owner loses `read`, and goes on hearing that the log moved. It hears nothing else, so what it gives away is when something was written, in any channel. Closing sockets past an age, so a client has to ask again, would bound that.
- **Schemas belong to the team and are guarded by the vibe.** `manage` at `*` on any one vibe registers a name and version for every vibe of the team, for good. A team that keeps vibes for different groups may want registering held to owners.
- **One scheduler queue for every team.** A pass takes the 50 longest-overdue schedules whoever they belong to, so one team's backlog delays another's. v1 is one deployment per organisation.
- **Every write wakes its vibe's hub.** The Worker can't know whether anyone listens, so each commit is one request to the Durable Object, off the response path, even when no socket is open. If it shows up on the bill, the hub can keep a count of its sockets in a place the Worker reads without waking it.
- **The upgrade goes around Elysia.** The response that opens a live socket is matched to its request by object identity. An Elysia release that hands routes a copy of the request would break `/live`, and only the `cf dev` run of the suite would notice.
- **A schema's patterns run on the Worker.** A `pattern` in a registered schema is a regular expression applied to data on every write that names it, and a bad one can be slow. Registering takes `manage` at `*`, and data is capped at 64 kB a message.
- **A watcher's secret is stored as it is.** Signing needs the secret itself, so D1 holds it in the clear, unlike a token, of which only a hash is kept. Whoever can read the database can forge deliveries to every watcher's endpoint.
- **A watcher sends requests to a URL someone chose.** Registering takes `manage` at `*`, the URL must be https unless it is the machine's own, and redirects are not followed. On a Worker a request can't reach a private network. Under `vibe serve` it can reach anything the machine can.
- **A delivery pass is a dozen queries a watcher, and a request an event.** A pass over a vibe reads each of its watchers' cursors, their registrant and their grants, whether or not anything matches. On D1's free plan an invocation gets 50 queries, so a vibe with more than a handful of watchers needs the paid plan's limit, as a busy scheduler already does.
- **Every write to a vibe with watchers is a queue message.** And every write to any vibe is one small read, to see whether it has a watcher. Both happen after the response.
- **A failing watcher holds its place forever.** Nothing gives up on a delivery, so an endpoint that never comes back is asked every hour for as long as the watcher exists, and its cursor falls behind without bound. If events are ever pruned, a cursor behind the horizon must stop the watcher loudly.
- **Revoking a token stops requests, not what its holder set going.** A schedule or a watcher its holder made carries on as its principal, and a live socket opened with it stays open, as below. Whoever revokes a token that leaked should look at `vibe schedules` and `vibe watchers` as well.
- **A person can revoke their last token.** Then only the operator, or GitHub sign-in where it is set up, lets them back in.
- **Any one credential can end all the others.** Whoever holds one of a person's tokens, or a session of theirs, can revoke the rest and stay in. The person then needs the operator. A token was always the person's whole access; this is a new thing to do with one.
- **A token that leaked may have made more than tokens and sessions.** Revoking it ends what it minted and opened. A service it added, with a token of its own, a grant, a watcher, a schedule and a sync entry all stay.
- **An entry's webhooks can be shut out by someone who knows its address.** While an address is over its budget for an entry's webhooks, a rightly signed webhook from there is refused too, and a platform sends everyone's webhooks from the same few addresses. Everyone who reads a vibe is shown its entries' webhook addresses. So one of them can point a repository or an app of their own at an entry and have the platform's servers use its budget up, at thirty wrongly signed events a minute. Checking the signature first and never refusing a right one would end that, and would bound nothing: the guess that lands is a right one.
- **A sync entry's webhook secret can be a word.** Nothing asks for a long one, and the README's own steps for Linear start an entry with a stand-in that anyone could sign with until the real secret is given. Thirty guesses a minute from an address is all that stands in front of a short secret.
- **Ownership is decided in several places, and a limit has to be remembered in each.** Deleting a message, canceling a schedule, an owner's change to a task, a keyed replay and posting a file each decide by who made the thing, and each had to be taught that a caller under a limit owns nothing its limit doesn't reach. A new rule that grants by ownership must ask `caller.narrowed` too. Nothing enforces that but review.
- **A limit with no profile shares its principal's unposted uploads.** A file is told apart by the actor that uploaded it. A handle narrowed with `as(null, { can })` writes as the principal itself, so it can post a file the principal uploaded and has not posted, given the file's ID. A delegated token always has a profile.
- **A limit that travels in a header binds the handle, not the holder.** `Vibe-Can` is for handing an agent's tool less than the process holds. Whoever has the token can send a request without it. A limit that must hold against its holder is a delegated token.
- **Signing in through GitHub has not been run against GitHub itself.** It follows GitHub's documentation of the device flow, and the tests play GitHub's part. A change in GitHub's answers shows up as `github_unavailable`, with GitHub's own words, and not before a real sign-in is tried.
- **The two sign-in routes take no token and call GitHub.** Anyone who can reach a Vibe can make it ask GitHub for device codes, against the limits GitHub sets for the app. Each address is held to ten starts in ten minutes. Nothing bounds all addresses together: a ceiling for everyone would let one caller close sign-in to the rest.
- **Budgets are counted by address, and an address is not a caller.** People behind one NAT, CI runners behind one egress and agents on one machine share a budget, except on the machine a `vibe serve` runs on, whose own connections are not counted. One of them retrying a revoked or expired token in a loop gets every credential from that address refused for the rest of each minute, the good ones included. The refusal says so and says when to come back, but nothing tells the others which process is at fault.
- **A caller with many addresses has a budget for each.** The limits bound one address, not a botnet, and an IPv6 network larger than a /64 is many callers. For the 200-bit secrets that changes nothing. For the operator's secret it is ten tries per address per ten minutes, so the secret has to be long and random, as the deploy instructions make it.
- **A refused credential is now a write.** Each refusal upserts a row in `attempts` until its address is over, where before it was one read. A caller that changes address with each request makes Vibe write a row a request, cleared by the next minute's pass. Cloudflare's own rate limiting, in front of the Worker, is the tool for that; none is configured.
- **Every request with a credential asks one more question of the database.** Whether its address is over, in parallel with the credential's own lookup. On D1's free plan that is one more of an invocation's 50 queries.
- **Guesses in flight together are all checked, except at the operator's secret.** For a token or a webhook's signature the count is read before the check and written after a refusal. A burst sent in the same instant is checked whole before the address is over. A webhook's secret is the platform's or a person's choice, so a short one is exposed to that.
- **Where the runtime gives no address, the limits are off.** A Worker always has one. Under `vibe serve` they are off for the machine's own connections, so behind a proxy on the same machine they are off for everyone until `--address-header` names the header the proxy sets. Behind a proxy on another machine everyone has that proxy's address, and one caller can use it up for all. A header the proxy doesn't set itself lets a caller choose who it is counted as.
- **An address over its budget is still checked, and only its answer is withheld.** The check runs alongside the question of whether the address is over. How long the refusal takes could tell a patient caller something of what it showed. At 200 bits there is nothing to learn that way.
- **An operator links a person to a GitHub login by its name.** Until that person first signs in, whoever holds the login at GitHub is them. After, it is the account's number that counts.
- **`vibe serve` keeps an owner's token in a file.** `.vibe/serve.json` is readable by its owner alone and ignored by Git, and so is the database. Anyone who can read the directory owns the Vibe in it.
- **A schedule outlives its author's tokens.** It fires for as long as its author is on the team and may post there. Revoking a token doesn't stop it; narrowing a grant, changing the role or canceling it does.
- **Schedules are uncapped, and a pass takes 50.** A person may hold any number, and a schedule whose firing keeps failing for a reason that isn't a refusal stays due and keeps its place at the head of each pass. More than 50 such would starve the rest.
- **Platform credentials open with the operator's secret.** They are sealed under a key derived from `VIBE_ADMIN_SECRET`, so whoever has the database and that secret has every entry's token. Changing the secret makes every entry's credentials unreadable: each has to be given again with `vibe sources credentials`. Nothing rotates them in place.
- **A synced channel is as readable as the platform channel it syncs with.** Grants don't apply on Slack, GitHub or Linear. Mapping a private vibe channel to a public Slack channel publishes it there, and only an owner maps. `noSync` is the one tool a writer has.
- **`sync` lets its holder write wherever the platform's app can.** A member with `sync` can start a thread in any Slack channel the app is in, mapped or not. An app invited only to the channels it maps bounds that.
- **Someone on Slack or Linear can mention anyone on the vibe by handle.** That is how a person there asks an agent for something. It also means a workspace member who is not on the team can page the team's people and agents. On GitHub, where strangers write, handles mention no one.
- **A webhook route takes no token.** Anyone who has an entry's ID can make Vibe verify a signature, which is one read and one decryption a request, thirty times a minute from one address before it is refused unread. An ID is not a secret kept anywhere but the platform's settings. A webhook for no entry costs one read and is never counted.
- **A platform gets one answer, after the work.** A webhook is answered once its event is applied, which is a handful of queries, and for a Slack user not seen before, a call to Slack. Slack retries an event not answered in three seconds, and the repeat is recognised by its ID. A slow D1 could turn that into a habit.
- **Slack is delivered to at least once.** A crash between Slack accepting a message and Vibe recording it sends the message again on the next pass. Linear's IDs are minted here, so its repeats are refused there. GitHub's mark only stops the copy coming back in.
- **A sync pass is a dozen queries an entry, and a call a copy.** As with watchers, a vibe with several entries needs D1's paid query limit, and a pass takes up 20 copies, so a long backfill drains over several passes.
- **An entry's `api` is an owner's to point anywhere.** Everything the entry sends, with its token, goes there. It is shown to whoever lists the entry and can't be changed afterwards, and redirects are not followed. Under `vibe serve` it can reach the machine itself.
- **The inbox holds what platforms sent.** Up to 200 events an entry, 32 kB each, in D1, readable by whoever holds `sync` at `*` and reads every channel the entry maps. A platform's payload can hold more than the message: who else is in a channel, an issue's whole body.
- **A session opened through GitHub ends only by itself, by signing out, or by being ended by name.** It has no token to end with, so a person who suspects one has to find it in `vibe sessions`, where all that tells sessions apart is what each browser said of itself and when it signed in.
- **On plain http, a session cookie is not bound to a port.** `vibe serve` on `127.0.0.1` shares its cookie with any other server on that address the same browser visits. `SameSite=Strict` and the origin rule keep other pages from using it; the other server would see it. Behind a proxy that ends TLS and forwards http, Vibe sees plain http: the cookie would lose `Secure` and sign-in is refused, until `vibe serve --public-url` says which address people use. Requests are then read as made to that origin, which trusts whoever can reach the port directly to be the proxy.
- **The page's access is the person's whole access.** A session is not narrowed, so a fault in the page that let a script run would act with everything its reader can do, for as long as the page stays open. The content policy, rendering Markdown without HTML and serving uploads as bytes are the layers against that.
- **Sync has not been run against a real Slack, GitHub or Linear workspace.** Every call and payload follows the platforms' documentation, and the tests play the platforms' part. A difference shows up as `message.sync_failed` with the platform's own words, or as an event the inbox marks `ignored` or `failed`, and not before a real workspace is connected.

## Open decisions

1. **Tenancy.** Assumed: `team_id` in every table, but v1 is operated as one deployment per organisation. A hosted multi-tenant service changes signup, billing, limits and the D1 ceiling above.
2. **Human login.** Tokens, and GitHub's device flow for a deployment that sets a client ID. The alternative stays open: put Cloudflare Access in front and write no auth code, at the cost of tying every user to one Zero Trust org.
3. **Store.** Assumed: D1 as the record, Durable Object as notifier only. Alternative: a Durable Object with SQLite per vibe as the record, which gives real transactions and per-vibe isolation but makes cross-vibe queries and migrations harder.
